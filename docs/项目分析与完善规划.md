## 二、后端分析

### 2.1 模块整体评价

项目中 **ruoyi-common / ruoyi-framework / ruoyi-system / ruoyi-generator / ruoyi-quartz** 六个模块完全保持若依官方源码，未做任何定制化修改，承担框架基础能力（认证、权限、日志、代码生成、定时任务）。实际业务代码仅存在于 `ruoyi-admin` 的 `com.ruoyi.devops` 包。

### 2.2 已实现业务代码（5 个 Java 文件）

```
com.ruoyi.devops
├── controller/WeeklyDailyOperationController.java   # REST CRUD
├── domain/WeeklyDailyOperation.java                  # 实体类
├── mapper/WeeklyDailyOperationMapper.java            # MyBatis 接口
├── service/IWeeklyDailyOperationService.java         # 服务接口
└── service/impl/WeeklyDailyOperationServiceImpl.java # 服务实现
```

**代码质量评估**：

- Controller 为标准若依 `BaseController` 继承，8 个接口（`list/get/export/add/edit/remove`），接口路径 `/dailyOperation`，权限前缀 `daily-operation:daily-operation:`。
- Service 层仅透传 Mapper，无任何业务逻辑。
- Domain 字段极为精简：`id / taskId / operationType / operationName / executor` + BaseEntity 审计字段。
- MyBatis XML 为标准 CRUD 模板，使用动态 SQL `<trim>` + `<if>`。

**结论**：代码为若依代码生成器产出，未进行任何二次开发，仅是一个"能跑"的 CRUD 骨架。

### 2.3 数据库设计（运维建表.sql）

共设计了 **4 张**运维业务表：

| 表名 | 设计完整度 | 现状分析 |
|------|:---:|------|
| `weekly_operation_task` | ⭐ | 仅 `id/report_id/create_time/creator`，大量字段被注释（任务名、执行人、需求方、日期、状态、需求描述、本周推进、问题风险等）。这是一张**关键主表**，但当前几乎不可用。 |
| `weekly_key_operation_detail` | ⭐⭐⭐⭐ | 完整的重点运维字段，14 个业务字段 + 审计字段。**但没有任何 Java 代码对应此表。** |
| `weekly_daily_operation` | ⭐⭐ | 简化的日常运维表，仅 5 个业务字段。**唯一有完整 Java 代码的表。** |
| `daily_inspection_main` | ⭐⭐⭐⭐⭐ | 设计最完整的巡检记录表，巡检日期/时间/人员/系统/IP/CPU/内存/磁盘/网络/告警/处理措施。**但没有任何 Java 代码对应此表。** |

### 2.4 配置层面问题

| 问题 | 严重程度 | 说明 |
|------|:---:|------|
| `application.yml` 中 `ruoyi.name: RuoYi` | 中 | 项目名称未自定义 |
| Token 密钥 `abcdefghijklmnopqrstuvwxyz` | **高** | 使用官方默认弱密钥，生产环境存在安全风险 |
| Redis 密码为空 | 中 | 无密码保护 |
| Druid 管理页用户名密码为 `ruoyi/123456` | 中 | 弱密码 |
| 验证码类型设为 `math` | 低 | 合理 |
| 未关闭 Swagger | 中 | 生产环境应关闭（`swagger.enabled` 当前为 `true`） |
| 暂无自定义菜单 `sys_menu` 数据 | **高** | SQL 中菜单数据完全是若依默认菜单，无运维业务模块入口 |

### 2.5 严重缺陷：表与代码不匹配

- `weekly_operation_task`（主表）→ **无 Java 代码**
- `weekly_key_operation_detail`（重点运维）→ **无 Java 代码**
- `weekly_daily_operation`（日常运维）→ **有代码，但表设计过于简陋**
- `daily_inspection_main`（巡检）→ **无 Java 代码**

### 3.3 已发现的 Bug

**删除接口 URL 拼接错误**：

```javascript
// ❌ 错误：多了一层 daily-operation 路径

// ✅ 正确：应匹配后端 /dailyOperation/{id}
url: '/dailyOperation/' + id
```

对比 `getDaily_operation` 使用 `url: '/dailyOperation/' + id` 是正确的，但 `delDaily_operation` 写错了。此 Bug 会导致**删除功能不可用**。

### 5.4 第三阶段：架构优化 + 质量提升

#### 5.4.1 安全性加固

| 项 | 建议 |
|------|------|
| Token 密钥 | 生成 64 位随机字符串替换默认值 |
| Redis 密码 | 设置强密码，生产环境建议使用 Redis ACL |
| Druid 监控 | 修改默认用户名密码，生产环境建议 IP 白名单 |
| Swagger | 生产环境关闭（`swagger.enabled: false`） |
| XSS 过滤 | 当前仅覆盖 `/system/*,/monitor/*,/tool/*`，需扩展覆盖 `/devops/*` |
| SQL 注入 | 检查所有 MyBatis 动态 SQL，确保 `${}` 改为 `#{}`（当前 mapper 已正确使用 `#{}`） |
| CORS | 确认跨域配置仅允许可信域名 |
| 敏感信息 | 数据库密码在 `application-druid.yml` 中明文存储，生产建议使用环境变量或配置中心 |

#### 5.4.2 性能优化

| 项 | 建议 |
|------|------|
| 数据库索引 | `daily_inspection_main` 已建 5 个索引，设计合理；其他表需补充：`operation_type`、`task_status`、`executor` 等常用查询字段 |
| 慢 SQL 监控 | Druid 已配置（`slow-sql-millis: 1000`），持续关注 |
| Redis 缓存 | 将字典数据（运维类型、状态枚举）、用户信息等热数据缓存 |
| 分页查询 | 所有列表查询已使用 PageHelper，可用 |
| N+1 查询 | 周报→明细的关联查询避免循环查 DB，使用 MyBatis 一对多映射或批量查询 |

#### 5.4.3 代码规范提升

| 问题 | 建议 |
|------|------|
| 包名混乱 | Controller 在 `com.ruoyi.devops.controller`，但 Domain 在 `com.ruoyi.devops.domain`——这是若依生成器的标准结构，保留。但建议将 `devops` 包统一放在 `ruoyi-admin/src/main/java/com/ruoyi/` 下 |
| Controller 路径前缀不统一 | 后端路径 `/dailyOperation` 无 `devops` 前缀，建议改为 `/devops/dailyOperation` 以区分业务域 |
| 前端 API 命名不规范 | `listDaily_operation` 混用驼峰和下划线，建议统一为 `listDailyOperation` |
| 缺少接口文档注释 | Controller 方法缺少 Swagger `@Operation` 注解的详细描述 |
| 缺少统一异常处理 | 业务异常应定义 `DevOpsException` 并注册到 `GlobalExceptionHandler` |
| 日志规范 | 关键业务操作（创建/修改/删除）应打印 INFO 级别日志，而非仅依赖 `@Log` 注解的切面 |

#### 5.4.4 架构层面建议

1. **独立 DevOps 模块**：建议将 `com.ruoyi.devops` 从 `ruoyi-admin` 中抽离为独立 Maven 模块 `ruoyi-devops`，遵循若依模块化理念。

   ```
   ruoyi-devops/
   ├── pom.xml (依赖 ruoyi-common)
   ├── src/main/java/com/ruoyi/devops/
   │   ├── controller/
   │   ├── domain/
   │   ├── mapper/
   │   └── service/
   └── src/main/resources/mapper/devops/
   ```

2. **前后端接口统一前缀**：后端 Controller 统一使用 `@RequestMapping("/devops/xxx")`，前端 API 统一使用 `/devops/xxx` 前缀。

3. **枚举值统一**：`operation_type`（运维类型）、`task_status`（任务状态）等应定义为 Java 枚举 `OperationTypeEnum`、`TaskStatusEnum`，避免魔法字符串。

4. **引入 MapStruct**：当前 Domain → VO 无转换（直接暴露 Domain 给前端），建议引入 MapStruct 做 DTO 转换，实现实体与接口隔离。

5. **巡检任务定时化**：日常巡检记录可通过 Quartz 定时任务自动生成（如每天早上 9:00 自动创建待巡检项），减少人工录入。

6. **考虑引入工作流引擎**：若运维流程较复杂（需审批环节），可考虑集成 Camunda 或 Flowable 轻量工作流引擎。
