## 描述

### 一、总则

本规范适用于公司各部门向衡泰技术有限公司提出的所有新增、优化、变更、修复类需求。

需求归口管理部门为信息技术部，由姚文隽统一负责收集、登记、编号、跟踪与闭环。

---

### 二、需求编号规范

**编号规则**：`[部门缩写]-REQ-YYYYMMDD-XXX`

| 字段 | 说明 |
|------|------|
| 部门缩写 | 固定 2 位英文大写（FI / SH / BJ / SZ / FIN / RM / OM / TD） |
| REQ | 需求固定标识 |
| YYYYMMDD | 需求提出日期（8 位） |
| XXX | 当日流水号（001 开始递增） |

**示例**：`FI-REQ-20260530-001`

---

### 三、需求命名规范

格式：`[优先级]-[部门]-[模块]-[内容]`

要求：无中文、无特殊符号、简洁明确

**示例**：`P0-FI-Trade-BatchImport`

---

### 四、需求优先级字典

| 优先级 | 含义 | 响应时效 | 排期时效 |
|--------|------|----------|----------|
| P0 | 紧急：影响核心交易/清算/估值 | 2 小时内响应 | 24 小时内提供方案 |
| P1 | 高：影响重要功能 | 1 个工作日内 | 3 个工作日内反馈排期 |
| P2 | 中：一般功能/体验优化 | 3 个工作日内 | 1 周内反馈排期 |
| P3 | 低：建议类 | 统一纳入需求池规划 | - |

---

### 五、需求状态流转

```
待分析 → 分析中 → 待确认 → 商务流程中 → 待排期 → 开发中 → 待验收 → 已上线
                                                                     ↓
                                                                  已驳回
```

---

### 六、Bug 验证闭环

Bug 修复后必须经过验证环节才可关闭：

```
待确认 → 已确认 → 修复中 → 修复完成 → 待验证 → 验证通过 → 已发布 → 已关闭
                                            ↓
                                        退回修复
```

**关键字段**：
- **补丁号（patch_no）**：标记本次修复对应的补丁版本
- **验证人（verifier_name）**：执行验证的人员
- **验证结果（verify_result）**：PASS / FAIL / REOPEN
- **实际上线时间（online_time）**：线上部署时间

### 七、需求管理全流程

| 步骤 | 负责方 | 说明 |
|------|--------|------|
| 需求收集 | 姚文隽 | 统一接收，当日完成初审与编号 |
| 周会评审 | 项目组 | 必要性、优先级、可行性评审 |
| 厂商分析 | 衡泰 | 次周周会反馈分析结果与工期评估 |
| 沟通确认 | 业务部门 | 1 周内完成确认 |
| 商务流程 | 业务部门+信息技术部 | 涉及采购立项的执行 |
| 需求确认 | 业务部门 | 商务完成后 2 周内完成最终确认 |
| 排期开发 | 衡泰 | 提供排期并按计划开发 |
| 测试验收 | 韩宝国/余如飞 | 验收不通过退回修复 |
| 上线闭环 | 信息技术部 | 验收通过后正式上线归档 |

### 九、管理要求

1. 所有需求必须走规范流程，禁止口头需求、私下变更。
2. 需求一经编号，全生命周期唯一，不得重复、不得删除。
3. 每周例会必须同步需求进展，逾期事项重点说明。
4. 验收不通过的需求，需明确问题并重新排期修复。
5. 衡泰需按约定时效响应、分析、交付，确保质量与进度。

### 十、附则

本规范自发布之日起执行，由信息技术部负责解释、修订与更新。

### 一、统一事项模型

统一事项是系统的核心聚合层。每一条运维记录 / Bug / 需求 / 变更 / 故障在创建或转换时，都会自动同步到 `ops_work_item` 表，形成一个全局统一的视图。

**如何运作**：

1. 用户在「运维记录」中录入一条日常运维活动。
2. 如果运维记录的类型是"问题处理"，可能发现是一个系统 Bug。
3. 在运维记录详情页点击「转 Bug」，系统自动：
   - 创建一条 `ht_bug_record` 记录
   - 创建一条 `ops_item_relation` 关系（CONVERT_TO）
   - 自动写回 `ops_issue.related_bug_no`
4. Bug 一旦创建，自动同步到 `ops_work_item` 统一事项表。
5. 在「统一事项」页面可以看到所有模块的事项汇总（只读）。

**状态映射**：

| 来源模块 | 来源状态 | 统一事项状态 |
|----------|----------|-------------|
| 运维记录 | PENDING | 待处理 |
| 运维记录 | PROCESSING | 处理中 |
| 运维记录 | CLOSED | 已关闭 |
| Bug | WAIT_CONFIRM | 待处理 |
| Bug | FIXING | 处理中 |
| Bug | VERIFIED / CLOSED | 已关闭 |
| 需求 | WAIT_ANALYSIS | 待处理 |
| 需求 | DEVELOPING | 处理中 |
| 需求 | ONLINE | 已关闭 |

### 二、模块联动

```
                    ┌─────────────┐
                    │  运维记录    │  ← 日常运维入口
                    │  (ops_issue)│
                    └──┬──┬──┬───┘
             转Bug    │  │  │   转变更
         ┌──────────┘  │  └──────────┐
         ▼            转需求         ▼
  ┌─────────┐    ┌─────────┐   ┌─────────┐
  │Bug管理  │    │需求管理  │   │变更记录  │
  └────┬────┘    └────┬────┘   └────┬────┘
       │              │             │
       └──────┬───────┴─────────────┘
              │ 自动同步
              ▼
       ┌───────────┐
       │ 统一事项   │  ← 全局聚合视图（只读）
       └─────┬─────┘
             │
             ▼
       ┌───────────┐
       │ 报告中心   │  ← 按时间范围导出 Word 报告
       └───────────┘

  运维记录 ←→ 巡检记录（issue_id 关联）
  运维记录 ←→ 故障记录（issue_id 关联）
  运维记录 ←→ 备份记录（issue_id 关联）
  故障记录 → 知识库（close 后可沉淀）
```

```
       │
       ├← ops_issue.work_item_id
       ├← ht_bug_record.work_item_id
       ├← ht_requirement.work_item_id

```
