## 一、系统定位

本系统不是简单的需求表和 Bug 登记系统，而是面向投资系统运维团队的**一体化运维与交付闭环平台**。

运维工作的本质是：**发现问题 → 分析问题 → 处理问题 → 验证结果 → 沉淀经验**。

这五个环节可以发生在一个值班人员处理参数配置的过程中，也可以发生在一条需求从提出到上线归档的几个月里。系统需要按统一的闭环逻辑管理所有运维活动。

## 二、核心业务模型

### 2.1 运维工作的完整闭环

```
日常值班 ─┐
巡检     ─┤
备份     ─┤
专项工作 ─┼─→ 运维事项 ─→ 分析处理 ─→ 验证确认 ─→ 知识沉淀
问题处理 ─┤
变更     ─┤
需求处理 ─┤
Bug      ─┘
```

### 2.2 运维事项的生命周期

所有运维活动都可抽象为"运维事项"，统一编码、统一流转、统一归档。

| 场景 | 说明 | 来源 |
|------|------|------|
| 问题处理 | 参数配置、数据修复、操作指导、系统异常 | 值班日志、巡检、客户群、电话 |
| 需求处理 | 新功能、功能优化、流程调整 | 业务部门、管理层 |
| Bug 处理 | 系统缺陷、接口异常 | 测试、巡检、用户反馈 |
| 变更处理 | 配置变更、数据变更、代码发布、环境调整 | 运维计划、问题驱动 |
| 专项工作 | 数据迁移、系统割接、应急演练、安全加固 | 年度计划、临时安排 |
| 巡检任务 | 日常巡检、月度巡检、专项巡检 | 值班排班 |
| 备份任务 | 全量备份、增量备份、恢复测试 | 运维规范 |

### 2.3 问题不等于 Bug

- **问题（Issue）**：一切需要运维介入的事项。可能是配置不对、数据异常、操作疑问、流程不清楚。
- **Bug（Defect）**：确认是系统代码缺陷，需要厂商修复。

一个问题经过分析后，可能的结论是：

| 处理方式 | 后续动作 |
|----------|----------|
| 修改配置 | 问题自行关闭 |
| 修改数据库 | 问题自行关闭 |
| 操作处理 | 问题自行关闭 |
| 转 Bug | 创建 Bug 记录，建立关系 |
| 转需求 | 创建需求记录，建立关系 |
| 转变更 | 创建变更记录，建立关系 |
| 无需处理 | 问题关闭 |
| 观察跟踪 | 定期复查 |
| 组合处理 | 多种方式并行 |

## 三、设计原则

### 3.1 参考平台与提炼

| 平台 | 可借鉴点 | 融入本项目的方式 |
|------|----------|------------------|
| ServiceNow ITSM | Incident 和 Request 分离；Problem 从多个 Incident 聚合；Change 受 Problem 驱动 | 运维记录分为事件和请求两个子类型；多个问题可聚合为一个 Bug 或需求 |
| Jira Service Management | Request Type 可配置不同字段模板；SLA 按优先级和类型设定 | 问题类型关联不同字段模板和 SLA 时效 |
| GLPI | Ticket → Problem → Change 三级模型；Change 有影响分析、部署计划、检查清单、回退方案 | 变更记录必须有影响范围、回退方案、执行检查清单、验证结论 |
| OpenProject | Work Package 统一表示任务/功能/Bug/变更；支持关联（blocks/blocked by/related/duplicates/child） | 事项关系支持 9+ 种类型 |
| Redmine | Tracker 区分 Bug/Feature/Support；不同 Tracker 配置不同工作流 | 闭环事项按来源类型配置不同状态流转 |
| 蓝鲸智云 | 作业平台、标准运维、CMDB 联动；故障自动触发巡检或修复作业 | 运维记录关联到系统资产和值班班次 |

### 3.2 核心设计原则

1. **统一入口、分类处理**：所有运维活动从统一入口进来，按类型走不同流程。
2. **闭环优先**：每件事必须有开始、处理、验证、关闭四个状态。
3. **关系驱动**：事项之间的关系比事项本身更重要——一个 Bug 从哪个问题来的、阻塞了哪个需求、通过哪个变更上线的。
4. **知识沉淀**：每次处理的经验不是写完就丢了，而是结构化沉淀到知识库。
5. **状态驱动权限**：不同状态下的可操作字段和按钮不同，避免误操作。

## 六、补丁号串联机制

补丁号 PATCH-YYYYMMDD-XXX 是串联 Bug、需求、变更的关键：

```
BUG-001 ──PATCH-20260530-001──→ CHG-001（变更）──→ 上线验证
FI-REQ-001 ──PATCH-20260530-001──→ CHG-001（变更）──→ 上线验证
```

同一个补丁号可以关联多个 Bug 和多个需求，通过变更一次性上线。

## 七、数据流转全景

```
值班日志 ─→ 登记问题 ─→ OPS-ISSUE-001 ─→ 分析 ─→ 改配置 ─→ 关闭
                              │
巡检记录 ─→ 发现异常 ─→ OPS-ISSUE-002 ─→ 分析 ─→ 转Bug ─→ BUG-001
                              │                    │
                              │          修复完成 → 验证 → 发布(CHG-001) → 关闭
                              │
备份失败 ─→ 登记问题 ─→ OPS-ISSUE-003 ─→ 分析 ─→ 转需求 ─→ FI-REQ-001
                              │                    │
                              │          验收 → 上线(CHG-002) → 关闭
                              │
                              └──→ 观察跟踪 ─→ 关闭

关闭事项 ─→ resolution_summary ─→ 知识库条目

所有事项 ─→ WorkItem ─→ 统一闭环 ─→ 报告中心 ─→ 周报/月报/复盘
```

## 八、实施计划

### P0（1-2 天）：闭环联动补全
1. 变更记录接入 WorkItem + Relation
2. Bug/需求创建时同步写 Relation
3. 转 Bug/转需求加幂等保护
4. WorkItem 状态变更回写源表
5. 前端按钮补 v-hasPermi

3. 巡检异常一键创建问题
4. 备份异常一键创建问题
